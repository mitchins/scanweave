# Independent review — current ClearScan semantic and measurement state

Reviewed commit: `08431a778f4373f7761ba796fdf631962738e5ae`.

## Findings

1. **Partial-span ownership and remapping look internally consistent.** In `crates/scanweave-io/src/convert.rs`, `visible_slots` is derived from units actually accepted into the emitted vector set; the per-character fallback skips only those OCR character ranges. Each incomplete span retains one whole-span `/ActualText` marked-content sequence while its emitted visible CIDs and missing-character CIDs are painted once. `crates/scanweave-io/src/document.rs::apply_remap` remaps the owner CID and every character CID through the same local-to-document map. In `page_pdf.rs`, per-character CIDs carry OCR character order and partial visible occurrences carry `visible_order`; emission sorts both and inserts missing characters by that order. This addresses the earlier bbox-center ordering hazard for the implemented left-to-right OCR ranges. The targeted `history-01-partial.pdf` extraction evidence from the prior review had the repaired `fimis` word once in Poppler and PDFium; current synthetic final metrics also report both renderers matching OCR after whitespace normalization.

2. **Semantic coverage remains bounded, and U+FFFE is not qualified away.** `CLEARSCAN_CONVERTER_REPORT.md` documents one PDFium U+FFFE replacing a hyphen on the separate frozen three-page comparison, also present in frozen pre-task ScanWeave output; Poppler extraction matched. The current 8-page synthetic fixture contains no hyphen in its supplied OCR (`300/final/metrics.json` and `600/final/metrics.json`), so its `search.*_matches_ocr: true` results do not test or close that defect. Preserve the claim as an inherited PDFium extraction limitation, and add a focused hyphen/soft-hyphen/Unicode extraction case before claiming cross-renderer semantic parity. No current evidence indicates the new character-level owner path itself creates duplicate text; its whole-span ActualText wrapper is singular by construction.

3. **Current exact-size renderer contract is materially better controlled.** `qualification/clearscan_competitive/compare.py` now uses integer-DPI Poppler and `math.nextafter(dpi/72, 0)` for PDFium exact-size renders, separately retaining default PDFium scale. This avoids the previously demonstrated page ceil and fractional Poppler phase shifts. The final metrics identify the renderer contract explicitly. Keep exact and default values separate; do not compare legacy fractional-Poppler scores with the new exact figures.

4. **The remaining glyph metric is useful for paired comparison, but its headline mean includes non-glyph windows.** `compare.py` scores every oracle record with a padded box (`pad=4` pixels), including whitespace records, then averages them into `summary`. The source baseline is therefore not a glyph-only mean (the old review evidence notes 48 space windows). Use `isolated_summary` and family/occurrence-level records for glyph appearance conclusions, and label the padded aggregate as a document-window score. A whitespace record whose crop has no foreground gets IoU 0 by the current `max(1, union)` rule; it is not meaningful evidence of glyph quality. Padded windows can also contain nearby glyph ink. The current exact-size 300 DPI values are source 0.9053, Poppler 0.8915, PDFium 0.8607; the isolated values in `metrics.json` are 0.9452, 0.9305 and 0.9108. At 600 DPI exact-size, padded values are 0.8998, 0.8517 and 0.8670; isolated values are 0.9781, 0.9270 and 0.9427. These support a cautious observation that this output is below source in these aggregate render metrics; they do not establish per-glyph regressions without stratified record analysis.

5. **Artifact/report freshness is not yet coherent.** `300/final/metrics.json` is 732,603 B / SHA-256 `515294f52a947153357a30a518f6bf7fb9b4eeb4ed1ed44f9fefd966897df725`; `600/final/metrics.json` is 1,334,401 B / SHA-256 `759d97eee08018ed9cd356277df22aef435f11fe03d2b767e6650e1848950433`. It predates the latest final runs and must not be presented as the current scorecard. `CLEARSCAN_CONVERTER_REPORT.md` likewise reports earlier 1,093,038 B / 889,147 B outputs and older visual scores; it is historical context, not the current result. ## Causal interpretation

The current artifacts support the observation that ScanWeave is far larger than matched Adobe XI (roughly 0.73 MB vs 37 KB at 300 DPI and 1.33 MB vs 51 KB at 600 DPI in the latest ScanWeave metrics; Adobe numbers are frozen). They also show the final exact-size renderer metrics remain below the source aggregate and that text extraction matches the supplied synthetic OCR after whitespace normalization. They do **not** isolate a single implementation cause for the visual gap: padded-window IoU combines fallback patches, accepted vectors, placement, font hinting/rasterization, and edge sampling. The metrics’ isolated glyph windows help, but conclusions should be based on per-family and per-occurrence comparisons, with renderer disagreements kept separate. Do not attribute the whole remaining gap to font reconstruction or background composition from these aggregate figures alone.

The exact-render correction resolves the earlier 1-pixel page-ceiling explanation for those runs; it does not itself prove that each PDF patch lands on the same sample grid as the source raster. The previously named fallback `8` remains a separate diagnostic and should only be closed by an occurrence-local crop comparison against its source patch under both renderers.
