# ACR04 codec integration: independent code review

**Review target:** working-tree diff from `8f14cd3` in `Cargo.lock`, `crates/scanweave-io/Cargo.toml`, `crates/scanweave-io/src/tonal_image.rs`, and `crates/scanweave-io/src/page_pdf.rs`.

## Findings

- **No concrete correctness blocker found in the encoding and PDF-resource path.** The writer changes the image dictionary dimensions when a full-page residual is reduced, but leaves the existing page placement matrix unchanged, so the image still covers the same physical page. The native exception path keeps source dimensions. Both new DCT resource identities include encoded bytes and dimensions, use distinct hash domains, and are followed by complete `ImageResourceKey` equality checks before reuse. The source-JPEG pass-through remains a later, explicit zero-visible-occurrence path; the new whole-page candidate excludes a verified source JPEG. The lossless public assembler is unchanged.
- **The progressive RGB correction is appropriately tested.** `optimized_jpeg` emits progressive scans for three-channel images, and the focused odd-dimension/color test exercises RGB decoding and partial MCU edges. This addresses the observed sequential-scan decoder issue without relying on a marker or producer-string assumption. The blinded visual renders also showed no color cast or chroma-edge damage in the red book stamp across PDFium and Poppler.
- **The lossy code is isolated to ClearScan assembly.** The new fallback assembler compares complete serialized lossless and compact PDFs and returns the shorter result; errors or non-beneficial encodings retain the lossless candidate. Document raster-baseline assembly still calls `assemble_document_with_options`, the public lossless assembler is unchanged, and ClearScan with explicit protected regions avoids the new path. Single-page ClearScan uses the same guarded helper.
- **Resource and eligibility checks are conservative and bounded.** Full-page candidates require one full-extent residual patch, no compact-background/source-JPEG path, at least 512×512 samples, at least 64 luminance levels, and no more than 16 MP. Reduced output is never upsampled and is accepted only when its encoded image stream beats the native Q85 representation by at least 5%; the final complete PDF must also be smaller. Native exceptions require at least 16×16, tonal content, a 512-byte lossless stream, and at least 5% stream savings before replacement. The new JPEG output is deterministic in the included tests.
- **The blinded visual result supports the 200-DPI path for the tested pages.** Before unblinding, all four arms were tied as visually acceptable on the specified financial, historical, receipt, mixed, and form-control crops in both renderers. After unblinding, this means the tested 200-DPI Q85 arm showed no material visible loss versus the native-resolution arms in those views. This is selected-page evidence, not an algorithmic quality guarantee for every eligible page.

## Reliability and cost limits

The production selection rule is size-based: after tonal and geometry gates, it does not decode the 200-DPI candidate and compare source-detail metrics before choosing it. That is consistent with the authorized lossy ClearScan experiment, but it means the selected-page visual review is the evidence for quality; a future change to eligibility or resampling should rerun the hard-to-see text, faded mark, color-edge, and both-renderer checks. The current thresholds can admit high-frequency or low-contrast content on a new document even when the image has many tonal levels.

Assembly deliberately builds both lossless and compact document candidates. Per eligible page it can encode a native Q85 image and a reduced Q85 image; fragmented pages may additionally try Q90 native exception patches. This has real CPU and peak-memory cost, bounded per image by the 16-MP check but not by a document-wide image count. I did not rerun the 32-document corpus or benchmark this working-tree version; the old sequential-encoder run does not qualify the new progressive output. Final runtime and renderer results should bind to the progressive build.

## Decision

No code-level blocker found for the bounded ACR04 integration. The code respects faithful/lossless assembly and ClearScan source/patch separation. The independent blind review found the tested 200-DPI arm acceptable, but this should not be presented as universal content fidelity. The final 32-document run and its runtime accounting remain the evidence gate for product-wide performance claims.
